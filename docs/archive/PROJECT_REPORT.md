## 一、项目目标

在腾讯云上构建"沙箱环境批量拉起 → Agent 自主解题 → TKE GPU 训练 → 新模型回沙箱评估"的完整强化学习闭环，用于 SWE-bench 类代码修复任务的模型能力提升。

### 验收标准

| 编号 | 验收标准 |
|---|---|
| A1 | SandBox 能批量拉起 SWE 题目环境（≥10 题），Agent 在沙箱中完成解题并输出结构化 tracing |
| A2 | 单条 tracing 包含完整操作序列（≥3 步操作）和最终测试通过情况 |
| A3 | TKE GPU 集群上 VERL 环境可正常运行，训练至少 50 step |
| A4 | reward 曲线呈上升趋势（提供图表） |
| A5 | 至少完成 1 轮完整闭环：SandBox 产出 tracing → TKE 训练 → 新模型回 SandBox 评估 |
| A6 | 训练后 pass@1 相比训练前有可观测提升 |

## 三、具体实现方法

### 3.1 整体架构

```
┌─────────────────────┐         ┌──────────────────────┐
│  TKE 集群（东京二区） │  公网    │  AGS 沙箱（新加坡）    │
│  2 × L20 GPU 节点    │ ──────▶ │  10 个 SWE-bench 题目 │
│  ┌────────────────┐ │  HTTPS  │  ┌─────────────────┐ │
│  │ verl Trainer   │ │         │  │ Agent 执行 bash  │ │
│  │ GRPO + LoRA    │ │         │  │ 运行项目测试套件  │ │
│  └───────┬────────┘ │         │  └─────────────────┘ │
│          │          │         └──────────────────────┘
│  ┌───────▼────────┐ │
│  │ vLLM 推理引擎   │ │         ┌──────────────────────┐
│  │ TP=2           │ │         │  CFS 共享存储          │
│  └────────────────┘ │ ──────▶ │  模型 / 数据 / 检查点  │
└─────────────────────┘         │  tracing / 日志       │
                                └──────────────────────┘
```

### 3.2 沙箱环境构建

- **镜像来源**：SWE-bench 官方 `sweb.eval` 镜像 + AGS 基底（含 `/init` 与 envd）重新打包，推送至 TCR `swe-mirror` 命名空间。
- **健康探针**：TCP 49983 + HTTP `/health`，缺失该探针会导致实例创建超时。
- **批量创建**：通过 `tccli ags CreateSandboxTool` 脚本化创建，参数除镜像外完全一致。
- **镜像预热**：`CreatePreCacheImageTask` 预拉取，避免首次拉起等待。

### 3.3 Agent 执行回路

每个 episode 的标准流程：

1. 沙箱内**预置目标测试补丁**，使 Agent 能直接运行测试获得执行反馈；
2. Agent 按轮次输出**一条 bash 命令**；
3. 沙箱执行命令并返回 `observation`；
4. 达到终止条件后导出候选补丁；
5. 在**全新沙箱**中应用补丁、运行官方 `eval.sh`、解析日志判分。

### 3.4 奖励函数

严格按验收口径实现：

```
reward = 通过的 FAIL_TO_PASS 测试数 / FAIL_TO_PASS 测试总数
resolved = 全部 F2P 通过 且 无 PASS_TO_PASS 回归
```

- 奖励仅来自沙箱内真实测试执行结果，无文本兜底、无模型自评；
- 判分使用官方 log parser，与 SWE-bench 口径一致。

### 3.5 训练配置

| 项目 | 配置 |
|---|---|
| 算法 | GRPO（`adv_estimator=grpo`） |
| 模型 | Qwen2.5-Coder-14B-Instruct（BF16） |
| 微调 | LoRA，rank=32，alpha=64，merge=False |
| 并行 | FSDP1 + vLLM TP=2，2 × L20 |
| 批次 | 每步 6 道训练题 × 每题 4 次采样 |
| 序列长度 | prompt 4096 / response 8192 |
| 训练步数目标 | 50 step |

### 3.6 工程保障机制

- **路由自检**：训练启动前校验数据表与沙箱工具映射一致，避免中途失败；
- **分阶段门禁**：先跑 2 步验证「组内奖励差异 + 非零梯度 + 检查点落盘」，通过后才启动 50 步；
- **快照冻结**：代码、数据、配置全量哈希，各阶段执行前校验，防止协议漂移；
- **证据留存**：所有轨迹、判分日志、GPU 采样、失败原文均归档，不覆盖历史实验。

### 4.4 模型与框架类（当前主要卡点）

**卡点一：30B MoE 模型无法在现有环境启动**

- 目标模型 `Qwen3-Coder-30B-A3B-Instruct`（MoE，128 专家）在 FSDP CPU offload 阶段报
  `torch.AcceleratorError: CUDA error: invalid argument`；
- 尚未进入 rollout，属框架与模型结构适配问题；
- **未修改驱动、未跳过错误、未提升权限**，按规则停止并保留日志。

**卡点二：14B LoRA 权重同步触发 CPU 内存溢出**

- 分层导出未识别到 adapter 参数，回退为**展开全量模型**，CPU 内存达 163.82GB / 170GB 触发 OOM；
- 已实现**基于参数归属的逐单元 adapter 导出**，双 GPU 数值回归通过；
- 14B 实机验证：每 rank 导出 672 个 adapter 张量、约 275MB，**不再展开全量模型，OOM 消除**。

**卡点三：GRPO 梯度为零（核心问题）**

- 7B 基座在训练集上产出补丁**全部无法通过任何 F2P 测试**，组内奖励恒为 0；
- GRPO 依赖组内奖励方差计算优势，全零即**梯度为 0，模型权重不更新**；
- 表现为 `actor/pg_loss = 0`、`critic/rewards/max = 0`，无论训练多少步曲线都不会上升。

**卡点四：训练仍在中断**

- 最近一次训练在 Django 题目判分时因必需测试未识别而按保护规则停止；
- 该问题与此前修复的日志解析属同类，正在进一步收敛。

## 六、未达成目标的原因分析

### 6.1 核心原因：训练集缺乏有效学习信号

这是 A4、A6 未达成的**根本原因**，且**不是工程实现问题**。

实测数据：

| 指标 | 实测值 | 含义 |
|---|---|---|
| `critic/rewards/mean` | 0.0 | 组内奖励均值全零 |
| `critic/rewards/max` | 0.0 | 连最大值都是零 |
| `actor/pg_loss` | 0.0 | 策略梯度恒为 0 |
| `actor/grad_norm` | 0.0 | 无梯度产生 |

机理说明：

> GRPO 通过"同一题多次采样的奖励差异"估计优势函数。若一组采样奖励全部相同（全为 0），优势为 0，梯度为 0，**模型参数不会发生任何更新**。因此在这种状态下，训练 50 步与训练 500 步结果相同，曲线必然平坦。

### 6.2 为什么奖励恒为 0

基座模型能力不足以完成 SWE-bench 真实缺陷修复：

- 模型能定位、能动手，但**写不出正确修复**；
- 观测到破坏性行为，例如整文件删除（将 61 行源码删空）；
- 训练集 6 道题全部如此，正奖励概率实测趋近于 0。

### 6.3 已采取的三项改进措施

| 措施 | 目的 | 效果 |
|---|---|---|
| 预置目标测试 | 让 Agent 能运行测试获得执行反馈 | 模型行为明显改善：会先跑测试再定向编辑 |
| 文件级定位提示 | 帮助模型定位改动点（仅给文件路径，不给代码） | 出现首个正奖励样本 |
| 切换 14B 稠密模型 | 提升基座能力 | Pilot 12 条轨迹中出现 1 条满分，**首次获得组内奖励差异** |

### 6.4 14B 的关键正向证据

在 14B Pilot 中：

- 12 条轨迹全部完成，无系统异常；
- `django__django-11039` 同一题两次采样分别得到 **1.0 分与 0.0 分**；
- 该样本产出 658 字节补丁，**完整修复并通过全部测试**；
- 校验结果 `informative_groups = 1`，**证明学习信号客观存在**。

> 结论：方案本身可行。当前问题在于**正奖励样本过于稀疏**，两步验证恰好未采样到正样本，因此未产生梯度。

### 6.5 资源约束的客观影响

| 约束 | 影响 |
|---|---|
| 仅 2 × L20（48GB × 2） | 30B MoE 无法容纳；14B 需 FSDP + 参数卸载，单步约 6–8 分钟 |
| 训练集仅 6 题 | 每步采样覆盖有限，正样本命中概率低 |
| AGS 跨区调用 | 单 episode 时延增加，50 步预计耗时较长 |
| 固定 GPU 节点 | 调试期间持续计费 |

- **工程链路已经打通**：10 题沙箱批量拉起、结构化 tracing、VERL 真实训练、检查点保存、自动化门禁与证据归档全部就绪；
