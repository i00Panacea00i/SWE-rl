## 0. 一页速览

### 我们做了什么？

训练了一个能**自主修复真实 GitHub 代码缺陷**的 AI 模型——不是调用现成 AI，而是用强化学习（GRPO）让模型在真实代码环境中反复做题、按测试通过率获得奖励、自主改进。

### 最终成果（一次完整训练运行）

| 指标 | 数值 |
|---|---|
| 训练步数 | **50 / 50 完成**（21 小时） |
| 轨迹总量 | **1692 条**（每条含完整操作/补丁/判分证据） |
| 满分轨迹 | 157 条（训练期 11.8%） |
| 奖励曲线 | 滑动平均 **0.042 → 0.119（+183%）**，趋势斜率 +0.00038/步，峰值 0.281 |
| 运行稳定性 | 零崩溃（中途一次 CPU 内存 OOM，修复后续训） |
| 评估（2 题） | 0.5（1/2 通过；样本小仅作 sanity check） |

### 系统全貌（一句话）

模型在**云沙箱**（AGS，每道题一个预构建镜像）中做题，**训练引擎**（verl + FSDP + vLLM，单机 4 卡）驱动"生成→执行→判分→更新"循环，所有数据与轨迹落在**共享存储**（CFS）上。

## 1. 硬件与基础设施

### 1.1 实际训练环境

```
腾讯云 VPC（东京）vpc-njm2vgou
├── TKE 集群 sichenggpuZ1（K8s 1.34.1）
│   └── GPU 节点 PNV5b.32XLARGE384
│       ├── 4× NVIDIA L20（48GB × 4 = 192GB 显存）
│       ├── 128 vCPU / 384 GB 内存
│       └── 子网 subnet-7k2qn2rx（NAT 出公网）
├── CFS 共享存储（NFS，模型/数据/轨迹/检查点）
└── （公网）AGS 沙箱平台 · TCR 镜像仓库
```

### 1.2 各组件的角色

| 组件 | 作用 | 类比 |
|---|---|---|
| TKE（Kubernetes） | 调度与运行训练 Pod | 写字楼的物业：分配房间和电力 |
| GPU 节点 | 执行模型计算（训练+推理） | 工作台 |
| CFS（共享文件存储） | 存放模型/数据/日志/轨迹（Pod 重启不丢） | 公共文件柜 |
| NAT 网关 | 集群访问公网（依赖下载、沙箱连接） | 大楼的对外大门 |
| TCR（镜像仓库） | 存放"题目环境"镜像 | 试题档案柜 |
| AGS（沙箱平台） | 提供隔离的做题环境（每轨迹一实例） | 一人一间的考场 |

### 1.3 资源账本（实测，重要经验）

| 资源 | 请求 | 实测峰值 | 结论 |
|---|---|---|---|
| GPU 显存 | 4×48GB | vLLM 115GB + FSDP 61GB（分片）| 可行，MoE 激活小是关键 |
| **CPU 内存** | **350Gi（下限）** | **~289GB** | **300Gi 会 OOM；30B 训练的真实内存 ≈ 3× 模型大小** |
| 共享内存 dshm | 32Gi | — | 64Gi 会加剧内存压力 |
| 单步耗时 | — | ~800 秒（13 分钟） | 8 题×4 次 = 32 轨迹/步 |

> **内存账单解释**：vLLM 休眠备份（~100GB）+ FSDP actor offload（61GB）+ ref offload（61GB）+ 共享内存（32GB）+ 引擎开销 ≈ 285GB。这是"colocate 单机训练 30B 模型"的最低硬件要求参考。

## 2. 软件架构总览

### 2.1 四层架构

```
┌─────────────────────────────────────────────────────────────────┐
│ 第 4 层 · 沙箱环境层（AGS 平台，公网）                              │
│   · TCR 题目镜像（每题一个：仓库代码@commit + 测试依赖 + envd 代理） │
│   · 通用工具 swe-ags（1 个，配合"镜像覆盖"服务所有题）               │
│   · e2b SDK 通道（训练进程 ↔ 沙箱的命令/结果传输）                   │
├─────────────────────────────────────────────────────────────────┤
│ 第 3 层 · 题目与判分层                                             │
│   · SWE-Gym tier-0 题（20 训练 + 2 评估，全部 golden 双向验证）      │
│   · 判分器（官方 eval.sh → F2P 通过率 → 奖励 0/1）                  │
├─────────────────────────────────────────────────────────────────┤
│ 第 2 层 · 训练引擎层（TKE Pod 内）                                 │
│   · verl 调度框架（RL 流水线）· FSDP（4 卡分片训练）                │
│   · vLLM 0.24（高速推理，TP=4，与训练共卡）                         │
│   · GRPO 算法（组内对比，每题采样 4 次）                            │
├─────────────────────────────────────────────────────────────────┤
│ 第 1 层 · 硬件与存储层（见第 1 节）                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 "共卡"设计（单机训练的核心工程）

同一组 GPU 既要"做题"（推理）又要"改模型"（训练），verl 的 colocate 模式 + 我们的补丁实现时序复用：

```
每个训练步（~800 秒）：
├─ 做题（Rollout ~690s）：vLLM 全速生成；FSDP 参数卸载在 CPU
├─ 判分（~30s）：干净沙箱跑官方测试 → 奖励
├─ 优势计算（~0.1s）：GRPO 组内对比
└─ 训练（~80s）：vLLM 休眠释放显存 → FSDP 反向传播 → LoRA 更新
   └─ 权重同步（~3s）：新 LoRA 逐单元搬回 vLLM（≤1.2MB/单元）
```

## 3. verl 训练框架详解

### 3.1 verl 是什么

字节跳动开源的大模型 RL 训练框架——把"出题 → 模型做题 → 判分 → 复盘改进"串成自动循环的**训练流水线**。

### 3.2 核心组件与角色

| 组件 | 角色 | 职责 |
|---|---|---|
| Actor | 学生（训练的模型） | 生成做题命令；接收梯度更新 |
| Rollout | 考试过程 | vLLM 高速生成每个动作 |
| AgentLoop | 监考老师 | 驱动"模型输出→沙箱执行→观察回填"循环（最多 12 步） |
| Reward | 判卷 | 沙箱官方测试通过率 → 0/1 |
| Ref / KL | 防跑偏约束 | KL 散度惩罚（系数 0.001） |
| FSDP | 参数管理 | 61GB 模型 4 卡分片 + 按需搬运 |
| vLLM | 推理引擎 | 生成回答（TP=4） |

### 3.3 GRPO 算法（为什么每题做 4 遍）

```
同一道题 → 4 个不同的解题尝试 → 4 个奖励
                ↓
组内比较：比同伴做得好的"动作序列"被强化
（4 个全对或全错 → 无学习信号；因此模型能力下限至关重要）
```

## 4. AGS 沙箱系统详解

### 4.1 为什么需要沙箱

模型做题需要真实可执行环境（仓库代码+依赖+测试），且必须隔离——沙箱 = 一人一间的考场。

### 4.2 沙箱构建流水线

```
DockerHub 官方镜像 → +envd 代理（端口 49983）→ TCR 私有仓库 → AGS 预热 → 实例
   xingyaoww/sweb.*     AGS 变体镜像      swe-mirror/swe-ags:*   4.2s 就绪
```

### 4.3 镜像覆盖（Image Override）—— 1 个工具服务 N 道题

AGS 账号级工具配额 30 个；采用**实例级镜像覆盖**突破限制：

```python
# 1 个通用工具（配额占用 1）：swe-ags
# 每次做题：创建实例时覆盖镜像（题 → TCR tag 规则：小写、__ → _s_）
StartSandboxInstance(ToolName="swe-ags",
                     CustomConfiguration={"Image": "…swe-ags:python_s_mypy-5617"})
# e2b SDK 接入（4.2 秒就绪）
sb = Sandbox.connect(instance_id)
```

### 4.4 训练进程 ↔ 沙箱通道

```
训练 Pod（AgentLoop）                      AGS 沙箱
  │ 1. 创建实例（镜像覆盖）─────────────────►│
  │ 2. e2b connect（HTTPS） ────────────────►│
  │ 3. 发送 bash 命令 ─────────────────────►│ 真实执行
  │ 4. 回传结果（stdout/exit_code） ◄────────┤
  │ 5. 循环 3-4（最多 12 轮）                 │
  │ 6. 导出补丁 ◄───────────────────────────┤
  │ 7. kill 沙箱 ─────────────────────────►│ 销毁
```

## 5. 一次训练步的完整数据流

### 5.1 数据流全景表

| # | 数据 | 从 → 到 | 通道 | 频率 | 量级 |
|---|---|---|---|---|---|
| 1 | 模型权重 | CFS → GPU 显存 | 文件读+PCIe | 启动+每步 | 61GB |
| 2 | 题库 | CFS parquet → 训练进程 | pandas | 启动一次 | MB 级 |
| 3 | 题目环境 | TCR 镜像 → AGS 缓存 | 预热 API | 部署时 | 1-2GB/题 |
| 4 | 沙箱创建 | 训练 Pod → AGS | HTTPS API | 32 次/步 | KB |
| 5 | 命令下发 | 训练 Pod → 沙箱 | e2b | ~10-12 轮×32/步 | KB/条 |
| 6 | 执行结果 | 沙箱 → 训练 Pod | e2b | 同上 | KB-MB/条 |
| 7 | 判分 | 判分沙箱 → 训练 Pod | e2b | 32/步 | 数值 |
| 8 | 奖励 | AgentLoop → GRPO | 进程内 | 32/步 | 数值 |
| 9 | LoRA 权重 | FSDP → vLLM | 逐单元（≤1.2MB） | 1/步 | 166MB/检查点 |
| 10 | 轨迹 | 训练 Pod → CFS | 文件写 | 32/步 | ~300KB/条 |
| 11 | 指标 | 训练 Pod → 日志 | console | 持续 | 1.4MB 全程 |

### 5.2 叙事版（一道题的完整生命周期）

1. **取题**：从题库取 8 道题
2. **建考场**：为每题向 AGS 申请独立沙箱（指定该题镜像，4 秒建好）
3. **答题**：模型通过 e2b 发命令（看代码/改代码/跑测试），沙箱执行回传，最多 12 轮
4. **交卷**：模型声明完成（SUBMIT），导出补丁
5. **判卷**：干净沙箱应用补丁 → 官方测试 → 通过率 = 得分
6. **复盘**：同题 4 次得分组内对比，"更好的做法"被强化
7. **存档**：全程轨迹落 CFS（可审计可复现）

## 6. 工程实践与踩坑修复（真实训练中的六项）

| # | 问题 | 根因 | 修复 | 效果 |
|---|---|---|---|---|
| 1 | 动作解析失败率 45% | 模型输出"思考+```bash 块"，旧解析器按混合内容拒绝 | 宽容解析（提取首个代码块） | 错误率 45% → ~0% |
| 2 | 命令被截断 | action_tokens 预算不足 | 1280 → 2048 | 长命令完整 |
| 3 | OAuth 刷新被限流 | 10 个 worker 并发刷新凭证 | 跨进程文件缓存+退避重试 | 只刷新一次全进程共享 |
| 4 | CPU 内存 OOM（286/300GB） | vLLM 备份+双模型 offload+64Gi 共享内存 | limit 350Gi、shm 32Gi、vLLM util 0.5、workers 8 | 稳定运行至完成 |
| 5 | 断点续训 | — | `resume_mode=auto` + 每 5 步 LoRA 存档 | OOM 后从 step 5 无损续训 |
| 6 | 多模态模型缺处理器文件 | Qwen3.5 系需要 preprocessor 文件 | 从 HF 补齐（换 30B 后无此问题） | 启动通过 |

## 8. 硬件选型记录

### 8.1 为什么是 4×L20 + 30B-MoE

| 候选 | 参数 | 推理成本 | 结论 |
|---|---|---|---|
| 7B Dense | 小 | 低 | 能力不足（实测成功率 0.7%，信号稀疏）|
| 14B Dense | 中 | 中 | 中等，非最优 |
| 32B Dense | 大（全激活） | 高（rollout 瓶颈）| 可行但慢 |
| **30B-A3B MoE** ✅ | 30B（激活 3B） | **低（≈3B 速度）** | **选定**：编码专长 + 推理经济 + vLLM 原生支持 |

### 8.2 显存与内存扩展需求（给后续扩容者的参考）

| 规模 | 显存 | 内存 | 说明 |
|---|---|---|---|
| 7B Dense 单卡 | 44GB | 120GB | 极限运行（曾用） |
| **30B MoE 4 卡** | **192GB** | **350GB** | **本次配置（健康）** |
| 32B Dense 4 卡 | 192GB | 350GB | 可行（推理慢于 MoE） |
| 下一档（更大模型）| 8×L20/H20 | 512GB+ | 内存 ≥3× 模型大小是铁律 |

## 9. 术语表

| 术语 | 一句话解释 |
|---|---|
| 强化学习（RL） | 通过"试错+奖励"让模型自己学会做对的事 |
| GRPO | 同题多次尝试、组内互比、优秀者被强化的 RL 算法 |
| LoRA | 轻量微调：只训练一小部分参数（166MB vs 61GB） |
| FSDP | 把大模型切片管理、按需搬运的训练技术 |
| vLLM | 高性能推理引擎（做题速度的来源） |
| Rollout | 模型做题的采样过程 |
| 沙箱 | 隔离的云端执行环境（一人一间考场） |
| 镜像 | 打包好的软件环境（代码+依赖），一次打包到处运行 |
| e2b SDK | 训练进程与沙箱的通信工具 |
| TKE / CFS / TCR / NAT | 腾讯云的 K8s / 共享存储 / 镜像仓库 / 公网出口 |
| 轨迹（Trajectory） | 一次做题的完整记录（每步指令+输出+得分） |
| F2P / P2P | 需"从失败变通过"的测试 / "必须保持通过"的回归测试 |
| 镜像覆盖 | 创建沙箱实例时动态指定题目镜像（1 工具服务 N 题） |
| colocate | 训练与推理共用同一组 GPU（时序复用） |
| KL 散度 | 衡量新旧模型差异（约束别学歪） |
