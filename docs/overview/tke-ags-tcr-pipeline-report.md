## 0. 执行摘要（一页看懂）

### 这套系统在做什么

让一个 30B 参数的大模型**在真实代码仓库里自主修复 GitHub 缺陷**——模型在云端隔离沙箱中执行自己编写的命令（改代码、跑测试），按测试是否通过获得奖励，通过强化学习持续改进。整个训练过程共产生 **1692 条完整"做题记录"**，全部可审计、可复现。

### 一句话架构

**TKE 出算力、AGS 出考场、TCR 出试题环境**——三者由训练程序串联成一条全自动流水线：

```
TKE 集群（东京一区）                  公网 HTTPS                   AGS 沙箱（新加坡）
┌───────────────────────┐                                     ┌────────────────────────┐
│  训练 Pod（4×L20 节点） │ ── 控制面：创建 / 销毁沙箱 ──────────► │  沙箱实例（一轨迹一间）   │
│   · vLLM：模型推理      │ ── 数据面：下发命令 / 回收结果 ─────► │   · 题目代码仓库         │
│   · FSDP：模型训练      │ ◄──────────── 回传 ───────────────  │   · 官方测试环境         │
│   · AgentLoop：调度器   │                                     └───────────┬────────────┘
└──────────┬────────────┘                                                 │ 拉取题目镜像
           │ 读写                                                          │（镜像已预热）
           ▼                                                               ▼
    CFS 共享存储（640GB）                                          TCR 镜像仓库
  模型 / 数据 / 轨迹 / 检查点 / 日志                          swe-ags:<题目ID>（每题一个镜像）
```

### 五个关键数字（全部实测）

| 数字 | 值 | 含义 |
|---|---|---|
| **4×L20 = 192GB 显存** | 单节点 | 承载 30B 模型训练的全部算力 |
| **50 步 / 21 小时** | 一次完整训练 | 产出 1692 条轨迹，终端零崩溃 |
| **~781 秒/步** | 单步耗时 | 其中 **89%（693 秒）花在模型"做题"**（生成命令）上 |
| **100 个沙箱** | 平台并发上限 | 训练按批调度（每步约 33 条轨迹并发） |
| **~5 秒** | 沙箱就绪 | 镜像预热后的实例创建耗时（冷启动需分钟级） |

## 1. 为什么需要这套 Pipeline：四条硬需求

训练一个"会修 bug 的模型"，本质上要让它**在真实环境里反复做题**。这个目标拆出四条硬需求，每一条都直接对应架构中的一个组件：

| # | 需求 | 通俗解释 | 对应组件 |
|---|---|---|---|
| 1 | **隔离执行** | 模型会执行任意代码（包括它有 bug 的代码），绝不能碰到任何生产系统 | **AGS 沙箱**（一轨迹一间隔离环境） |
| 2 | **环境精确复现** | 每道题必须在"该代码仓库的指定版本 + 精确依赖"下运行，否则测试结果无意义 | **TCR 镜像仓库**（每题一个预构建镜像） |
| 3 | **长跑不中断 / 可恢复** | 21 小时连续训练不能因一次故障归零 | **TKE 集群 + CFS 共享存储**（可续训检查点） |
| 4 | **可审计 / 可复现** | 每一条命令、每一次判分都要有据可查（训练效果验证的底线） | **全链路证据链**（命令级 + 判分级落盘） |

这四条需求共同排除了"本地直接跑"的方案——它同时需要**云上 GPU**（算力）、**隔离沙箱**（安全）、**镜像仓库**（环境一致性）与**共享存储**（持久化）。

## 2. 组件职责与交互关系

### 2.1 组件清单（六个角色）

| 组件 | 云服务 | 职责 | 通俗类比 |
|---|---|---|---|
| **TKE 集群** | 腾讯云 Kubernetes | 调度并运行训练 Pod；管理 GPU 节点 | 写字楼物业：分配房间和电力 |
| **GPU 节点** | PNV5b 机型 | 4×L20 执行全部模型计算（推理+训练） | 工作台 |
| **训练 Pod** | 自研程序 | 运行 RL 训练主循环：生成→执行→判分→更新 | 流水线总控 |
| **CFS 共享存储** | 弹性文件存储 | 存放模型、数据、轨迹、检查点、日志（Pod 重建不丢） | 公共文件柜 |
| **AGS 沙箱平台** | Agent Sandbox | 为每条轨迹提供隔离的"做题环境" | 一人一间的标准化考场 |
| **TCR 镜像仓库** | 容器镜像服务 | 存放每道题的预构建环境镜像（代码+依赖+通信代理） | 试题档案柜 |

### 2.2 交互关系总图（谁调用谁）

```
                    ┌───────────────────────────────┐
                    │        训练 Pod（TKE 内）        │
                    │  ┌─────────────────────────┐  │
   ① 调度运行 ──────►│  │ AgentLoop（rollout 调度） │  │
                    │  │  ├─ vLLM：生成命令        │  │
                    │  │  ├─ 沙箱客户端：下发/回收   │  │
                    │  │  └─ 判分器：重放补丁跑测试  │  │
                    │  └─────────────────────────┘  │
                    └───┬──────────┬──────────┬─────┘
                        │          │          │
        ② 控制面（建/销沙箱） ③ 数据面（命令/回传） ④ 持久化（读写）
                        │          │          │
                        ▼          ▼          ▼
                ┌───────────┐ ┌────────┐ ┌──────────┐
                │ AGS 控制台 │ │ 沙箱实例 │ │   CFS    │
                │  （API）   │ │ (envd)  │ │  存储    │
                └─────┬─────┘ └────┬───┘ └──────────┘
                      │            │ ⑤ 镜像拉取（实例启动时）
                      └────────────┼────────────┐
                                   ▼            ▼
                            沙箱内执行 bash   TCR 镜像仓库
```

**五种交互的通道与凭证**（全部为 HTTPS 加密连接）：

| # | 交互 | 发起方 → 接收方 | 通道 / 凭证 | 频率 |
|---|---|---|---|---|
| ① | 调度运行 | TKE → Pod | K8s 内部调度 | 一次（训练期） |
| ② | 建/销沙箱 | Pod → AGS API | 腾讯云 SDK + oauth 凭证（自动续期） | 每轨迹 1 建 1 销（总约 4000 次） |
| ③ | 命令/回传 | Pod → 沙箱 envd | e2b 协议 + API Key | 每轨迹 ≤12 轮（全程约 3 万次往返） |
| ④ | 持久化 | Pod ↔ CFS | NFS 挂载（同 VPC 内网） | 持续（每条命令即时落盘） |
| ⑤ | 镜像拉取 | 沙箱 → TCR | 企业镜像仓库（已预热） | 每实例 1 次（~5 秒，预热后） |

> **【截图占位 ② · AGS 沙箱实例】**
> - **控制台路径**：Agent Sandbox（AGS）控制台 → 实例列表 / 工具列表
> - **建议画面**：实例列表（训练时段批量创建记录）+ 通用工具 `swe-ags`
> - **配文**：每个沙箱实例服务一条轨迹；全部题目共享 1 个通用工具，靠"镜像覆盖"实现配额优化

### 2.3 三个关键设计（为什么这样分工）

| 设计 | 做法 | 收益 |
|---|---|---|
| **镜像覆盖**（AGS + TCR 协作） | 只创建 1 个通用沙箱工具，把题目镜像作为"创建参数"传入 | 平台工具配额占用从"每题 1 个"降到 **1 个**，服务任意题量 |
| **培训同管道** | 训练与评估用同一套沙箱通道、同一判分器 | 训练指标与评估结果**口径一致**，对比可信 |
| **判分隔离** | 判分在**全新沙箱**中重放模型补丁后运行官方测试 | 模型全程看不到判分过程与标准答案，杜绝作弊 |

## 3. 控制流：一次训练任务的完整生命周期

从"提交训练任务"到"产出 50 步模型"，控制信息按以下顺序流转：

```
① 提交任务       运维执行 kubectl apply（训练 Pod 清单）
    │            └─ TKE 调度到 4×L20 节点（约 1 分钟）
    ▼
② 环境装载       Pod 启动：挂载 CFS（模型/数据）、装载 oauth 凭证 Secret
    │            └─ 真实日志："[validate_config] All configuration checks passed successfully!"
    ▼
③ 引擎自检       vLLM 加载模型分片（TP=4）+ FSDP 初始化 + Ray 集群就绪
    │            └─ 检查 CFS 是否有历史检查点（断点续训机制）
    ▼
④ 训练循环（×50 步，每步 ~13 分钟）
    │  每步：建沙箱 → 模型生成命令 → 沙箱执行 → 回传 → 判分 → 梯度更新 → 销沙箱
    │  （详见第 4 节数据流）
    ▼
⑤ 检查点        每 5 步保存 LoRA 适配器（166MB/个）→ CFS
    │            └─ 作用：任何中断损失 ≤ 1.5 小时
    ▼
⑥ 训练完成      第 50 步：合并模型 + 归档轨迹 → CFS
    │            └─ 真实日志：训练 21 小时，期间一次故障后无损续训
    ▼
⑦ 独立评估      同一集群另起评估 Pod（base vs 训练后模型，40 题对照）
```

## 4. 数据流：三个平面的流转方式

训练过程中有三类数据在流动，走向完全不同：

### 4.1 沙箱命令流（每轮交互 · 约 3 万次）

这是最高频的流转——模型的每次"动作"都要经历一段完整旅程：

```
模型生成一条 bash 命令（在 GPU 上）
   │
   ▼ ① Pod 侧加"5 层防护"（约毫秒级）—— 不让原始命令直接进沙箱
   │     · 环境注入：保证 conda 环境路径     · 语法预检：不完整命令直接拦回
   │     · 超时双保险：120 秒强制终止        · 输出截断：防巨型日志撑爆回传
   │     · 目录锚定：固定工作目录 /testbed
   ▼
② HTTPS 跨区域传输（东京 → 新加坡，约 0.3-1 秒）
   │
   ▼
③ 沙箱内执行（真实耗时 0.10 - 2.50 秒）
   │     在 Debian 13 环境中运行，工作目录为题目代码仓库
   ▼
④ 结果原路回传：stdout/stderr + 退出码（真实回传示例，262 字符）
   │     exit_code=0
   │     /testbed/dvc/tree/ssh/__init__.py
   │     /testbed/tests/unit/remote/ssh/test_ssh.py
   ▼
⑤ Pod 侧截断至 512 token → 作为"观察"回填对话 → 模型决定下一步
```

**真实数据的三个佐证**（来自 1314 条命令的实测统计）：

| 观测项 | 实测结果 | 说明 |
|---|---|---|
| 退出码分布 | 成功 94.8% / 测试失败 3.0% / 其他 2.2% | "失败"绝大多数是**正常的测试反馈**，不是通信故障 |
| 单命令执行耗时 | 0.10 - 2.50 秒 | 沙箱内纯执行时间（不含模型生成时间） |
| 输出保护命中 | 最大单次输出 32,803 字节（精确命中 32KB 上限） | 截断机制真实生效：保留头 8KB + 尾 24KB |

### 4.2 训练数据流（每个训练步 · 50 次）

```
训练题库（parquet）      →  每步抽 8 题 × 每题 4 次采样 = 约 33 条轨迹
        │
        ▼ rollout（约 693 秒，占单步 89%）—— 全部在沙箱中完成"做题"
        │
        ▼ 每轮交互即时落盘（即使进程崩溃，已完成部分不丢）
        │     episode.json（对话与命令） + execution.json（命令级证据）
        ▼
判分（独立沙箱重放补丁 → 跑官方测试）→ 奖励 0/1
        │
        ▼ 组内对比（GRPO：同题 4 次采样互相比）→ 优势值
        │
        ▼ 梯度更新（LoRA，约 26 秒）→ 新权重
        │
        ▼ 权重同步（约 3 秒）→ 回到 vLLM 供下一轮生成
```

**单步耗时的真实分解**（step 6 日志原文摘录）：

```

timing_s/old_log_prob: 32.3   ← 策略概率重算
timing_s/ref: 29.4 秒         ← 参考模型前向（防跑偏约束）
timing_s/adv: 0.06 秒         ← 优势值计算
perf/time_per_step: 781.3 秒  ← 单步总耗时
perf/throughput: 62.8         ← 吞吐（token/秒/卡）
critic/rewards/mean: 0.125    ← 本步平均奖励
response_length/mean: 4468    ← 平均响应长度（token）
```
> 日志来源：`train-20260918T110822Z.log` 第 1444 行（step 6）
> 管理解读：**训练时间花在"做题"上（89%），而不是"改模型"上（约 3%）**——这正是这套架构的预期形态。

### 4.3 持久化流（CFS 上的资产清单）

| 目录 | 内容 | 规模 |
|---|---|---|
| `model/` | 基座模型（16 分片） | 61.1 GB |
| `checkpoints/` | 每 5 步 LoRA 检查点（四件套） | 166 MB/个 × 10 |
| `traces/` | **1692 条轨迹证据链**（对话 + 命令 + 补丁 + 判分日志） | 数 GB |
| `logs/` | 训练日志 + GPU 监控（每 30 秒采样） | 约 2.5 GB |
| `data/` | 训练题库与评估题库 | 数十 MB |

> **轨迹证据链的意义**：每条轨迹的目录里包含 `episode.json`（完整对话与每步的 action/observation/reward）、`agent/execution.json`（每条命令的 stdout/退出码/耗时）、`candidate.patch`（模型产出的代码补丁）、`judge/test.log`（判分沙箱内的官方测试完整输出）。**训练效果的任何结论都能逐条回溯到证据**。

## 5. 镜像供应链：TCR 的角色（为什么不能省）

### 5.1 一道题的"环境"包含什么

每道题的镜像 = 代码仓库（指定版本）+ 全部测试依赖 + 通信代理（envd）。没有这个镜像，模型改完代码无法在"与出题时一致的环境"中验证——**测试结果就失去意义**。

### 5.2 供应链四步（从公开源到就绪沙箱）

```
① 公开源镜像（Docker Hub）           ② 批量转存/构建（一次性）
   xingyaoww/sweb.eval.x86_64.*   →   <企业镜像仓库>/swe-mirror/swe-ags:<题目ID>
   （每题一个，事前已确认存在）           （内部企业仓库，121 题已全部转存）
                                              │
                                              ▼
④ 沙箱就绪（~5 秒）                 ③ 镜像预热（一次性，提前完成）
   AGS 用 TCR 镜像创建实例         →   预热任务（121 题全部预热完成）
   （冷启动需分钟级，预热后秒级）        （把"拉镜像"成本移到训练开始之前）
```

### 5.3 关键机制：镜像覆盖（1 个工具服务全部题目）

| 维度 | 旧做法（逐题工具） | 现做法（镜像覆盖） |
|---|---|---|
| 平台工具数量 | 每题 1 个（28 题 = 28 个） | **1 个通用工具 `swe-ags`** |
| 镜像绑定时机 | 创建工具时固定 | **创建实例时动态指定** |
| 配额占用 | 28/30（几乎用满） | 1/30（释放全部扩展空间） |
| 实例创建耗时 | — | **实测 4.2 秒**（镜像已预热） |

命名规则（供应链的一致性保障）：题目 ID 经确定性转换得到镜像标签，构建脚本与运行代码**共用同一条规则**，无需维护映射表：
```
python__mypy-5617  →  swe-ags:python_s_mypy-5617   （`__` 统一转义为 `_s_`，全小写）
```

> **【截图占位 ④ · TCR 镜像仓库】**
> - **控制台路径**：容器镜像服务 TCR → 企业版实例 → 镜像仓库 `swe-mirror/swe-ags`
> - **建议画面**：镜像 tag 列表（题目 ID 命名的镜像）+ 镜像大小

## 6. 架构在真实运行中的表现

### 6.1 性能账（50 步训练实测）

| 指标 | 实测值 | 说明 |
|---|---|---|
| 单步耗时 | 781 秒（约 13 分钟） | 全程稳定（步骤间波动 <6%） |
| 生成占比 | **89%**（693/781 秒） | 时间主要花在模型"做题" |
| 训练吞吐 | 62.8 token/秒/卡 | 随输出长度增加而略升 |
| 单卡显存占用 | 约 24 GB / 45 GB | 余量健康，全程无显存故障 |
| CPU 内存占用 | 约 242 GB / 350 GB 上限 | 曾因 300GB 上限发生一次 OOM（见 6.4） |
| GPU 利用率监控 | 每 30 秒采样落盘（`gpu.csv`） | 全程可回溯 |

### 6.2 可靠性账（长跑 21 小时为什么不断线）

| 机制 | 解决什么问题 | 真实效果 |
|---|---|---|
| 凭证自动续期 | 长跑期间云 API 凭证过期 | 21 小时零凭证故障 |
| 三层超时防护 | 挂起命令 / 僵尸沙箱 / 创建卡死 | 命令 120s、实例 30 分钟、就绪等待 90s |
| 输出截断 | 巨型日志撑爆回传与模型上下文 | 单条上限 32KB（实测精确命中） |
| 配额调度 | 平台并发上限 100 个沙箱 | 按批调度 + 建前探针，零超限失败 |
| 检查点四件套 | 故障后从头训练 | 每 5 步存档，故障恢复**零损失**（实测） |
| 双重校验 | 跑错镜像版本出假结果 | 沙箱代码版本必须与题目基准版本一致 |

### 6.3 成本账（规模单位）

| 规模单位 | 通信/计算操作 | 实测 |
|---|---|---|
| 1 条命令 | 1 次跨区域 HTTPS 往返 + 沙箱内执行 | 0.1 - 2.5 秒 |
| 1 条轨迹 | 1 次沙箱创建 + ≤12 轮命令 + 1 次判分 + 1 次销毁 | 25 - 40 分钟（含模型生成） |
| 1 个训练步 | 约 33 条轨迹并发 | 13 分钟 |
| 完整训练 | 50 步 ≈ **4000 次沙箱生命周期** | 21 小时 |
| 完整评估 | 320 条轨迹（两组模型对照） | 4 批 × 30 分钟 |

### 6.4 一次真实故障的完整复盘（架构韧性的最好证据）

```
现象：训练至第 5 步时 Ray 报 CPU 内存不足（实测 286GB / 上限 300GB）
根因：30B 模型"共卡训练"的内存需求 ≈ 3× 模型大小
      （vLLM 休眠备份 100GB + actor 61GB + 参考模型 61GB + 共享内存 32GB）
修复：内存上限 300→350GB + 共享内存 64→32GB + 推理显存占用 0.6→0.5
结果：从 step-5 检查点**无损续训**，最终 50/50 步完成
沉淀：内存下限 350GB 成为可复用的最小可行配置
```
> 这一案例同时验证了两个设计：**检查点机制**（故障不丢进度）与**共享存储**（Pod 重建后模型/数据/进度全部在 CFS 上）。

## 7. 架构评价与改进方向

### 7.1 三个"设计正确"的决策

1. **隔离优先**：模型代码只在沙箱中执行，与生产系统物理隔离——这是安全底线，也是能放心让模型"自由发挥"的前提；
2. **证据链优先**：命令级证据 + 判分级日志全量落盘，使"训练有没有效果"这类问题**永远可以用数据回答**（本项目多次依靠证据链定位根因）；
3. **共享存储优先**：模型、数据、轨迹、检查点全部落在 CFS——训练 Pod 成为"可随时重建的消耗品"，这是 21 小时长跑敢用云端资源的前提。

### 7.2 三个已知边界

| 边界 | 现状 | 影响 | 改进方向 |
|---|---|---|---|
| 沙箱并发上限 100 | 平台配额 | 单步轨迹数受限（当前约 33 条/步未触顶） | 如需更大采样，提前申请提额或分批 |
| 跨区域网络 | Pod 在东京、沙箱在新加坡 | 单次命令增加约 0.3-1 秒延迟 | 同区域部署（如需进一步压缩步耗时） |
| 单节点算力 | 4×L20（LoRA 训练 30B 的上限配置） | 无法全参微调、无法跑更大模型 | 扩容至 H20 级节点（显存 96GB/卡） |

### 7.3 下一步扩容论证（一页结论）

当前配置已把"单节点 4×L20 训练 30B-MoE"推到工程极限（跑通 + 闭环验证完成）。能力继续跃升需要更大显存：
- **现状**：44GB/卡 → 只能 LoRA（约 0.09% 参数参与训练）
- **扩容后**（2×H20，96GB/卡）：可全参微调 32B / LoRA 训练 70B，推理 KV 容量大幅提升

## 8. 术语表（管理者版）

| 术语 | 一句话解释 |
|---|---|
| Pod | 云上运行训练/评估程序的容器（本系统的"总控"） |
| TKE | 腾讯云 Kubernetes 服务——负责调度和运行 Pod |
| CFS | 共享文件存储——模型、数据、轨迹、检查点的"公共文件柜" |
| AGS | Agent Sandbox——腾讯云隔离沙箱平台（"云端考场"） |
| TCR | 腾讯云容器镜像仓库——存放每道题的环境镜像（"试题档案柜"） |
| 沙箱 / 实例 | 一条轨迹专属的隔离做题环境（一道题的"考位"） |
| envd | 沙箱内部的通信服务（接收命令、执行、回传） |
| e2b | 沙箱通信协议标准（AGS 兼容实现） |
| 镜像覆盖 | 1 个通用工具 + 按题切换镜像——把平台工具配额从 28 个降到 1 个 |
| 轨迹（episode） | 一次完整"做题过程"（≤12 轮命令交互 + 判分） |
| rollout | 让模型对同一道题做多次尝试（用于组内对比学习） |
| GRPO | 强化学习算法——同题多次尝试互相比，好的方向被强化 |
| LoRA | 参数高效微调——只训练约 0.09% 的参数，使 30B 模型能在 4 卡上训练 |
| 检查点 | 训练进度的存档（含模型/优化器/随机数/学习率），用于故障恢复 |
| pass@4 | 同一题 4 次尝试中至少成功 1 次（衡量"会做但不稳"） |
