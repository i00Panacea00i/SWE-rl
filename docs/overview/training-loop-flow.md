# 训练闭环流程全解：SandBox → TKE → 新模型 → SandBox

> **汇报要点**：本项目的核心工程是打通一条**自动化闭环**——
> ① 云沙箱（AGS）里让模型做题并**全程留痕**（tracing）；
> ② TKE 集群消费痕迹做 **RL 训练**（GRPO）；
> ③ 训练出的**新模型回到同一沙箱**接受同协议验证；
> ④ 验证结论**回流**指导下一轮数据与配置。
> 全程判分同源、协议同构、证据可溯——每个数字都能追到原始记录。

## 1. 阶段 A · SandBox 产出 Tracing（数据采集）

### 1.1 谁在做题

基座模型（Qwen3-Coder-30B-A3B）按**固定 Agent 协议**在沙箱中解题：
每轮输出"思考 + 一条 bash 命令" → 沙箱执行 → 结果返回 → 下一轮（最多 12 轮）。

### 1.2 每次交互的产物（5 类文件，全部落盘）

| 文件 | 内容 | 规模 |
|---|---|---|
| `episode.json` | 完整对话（20 条消息级） | ~34KB/条 |
| `execution.json` | **每条命令**的证据（命令/退出码/stdout/stderr/耗时） | ~2-19KB/条 |
| `candidate.patch` | 模型最终代码修改（净产出） | 几百 B ~ 几十 KB |
| `result.json` | 判分结果（f2p/p2p 通过清单、resolved） | ~5KB |
| `test.log` | 官方测试完整日志（判分时在独立沙箱生成） | 3KB+ |

### 1.3 真实案例（一条成功轨迹）

```
模型命令   : python -m pytest ... test_ssh_allow_agent[config3-False]
AGS 回传   : exit_code=0 + 6 个文件路径
...
模型命令   : find /testbed -name "patches.py" -type f
AGS 回传   : /testbed/conan/tools/files/patches.py（0.133s）
...
最终判分   : 28 passed in 0.49s → reward=1.0 / resolved=True
```

### 1.4 量级

| 用途 | 轨迹数 | 说明 |
|---|---|---|
| 训练期（50 步 × 32） | **1692 条** | 全部有命令级证据（3384+ 份 execution.json） |
| 评估期（40 题 × 4 × 2 组） | **320 条** | base vs lora 对照 |
| 数据质量验证（更早） | 数百条 | 双向验证（baseline 失败 + golden 通过） |

## 2. 阶段 B · TKE 训练（消费 Tracing）

### 2.1 数据入口

轨迹转换为训练 parquet：每题含 **prompt（系统+题面）** 与 **extra_info**
（instance_id / 镜像地址 / 基础分片等）——训练进程按需拉起沙箱。

### 2.2 单步内部流程（~13 分钟/步）

```
① rollout：     vLLM 为 8 题 × 4 采样生成动作（每轮最长 2048 token）
② 沙箱执行：    动作送 AGS 沙箱执行（8 并发 worker）——即"阶段 A"的采集过程
③ 判分回填：    每题终态导出补丁 → 独立沙箱判分 → 奖励 = f2p 通过比例（0~1 连续）
④ GRPO 更新：   同题 4 采样为一组 → 组内标准化算优势 → 反向传播更新 LoRA
⑤ 权重回流：    更新后的 LoRA 增量同步给 vLLM（layered_summon，逐单元 ≤1.2MB）
```

**每一轮 rollout 又产出新 tracing**——这就是闭环的"数据自产"特性。

### 2.3 训练实录（50 步）

| 指标 | 结果 |
|---|---|
| 奖励滑动平均 | 0.042 → 0.119（+183%） |
| 单步耗时 | 840s → 770s |
| 产出 | 50 个检查点（每 5 步）+ 最终 HF adapter（53.5MB） |

## 3. 阶段 C · 新模型回 SandBox（验证）

### 3.1 权重回流路径

```
LoRA 增量（53.5MB，HF adapter）
   → 离线合并 W + α/r·B@A（纯 safetensors，192/18867 张量）
   → 完整模型（61.1GB，16 分片）
   → vLLM 加载（TP=4）——与基座完全同路径（公平性）
```

### 3.2 评估协议（与训练同构）

40 题 heldout（与训练 0 重叠）× 4 采样 × temp 0.7；协议参数与训练逐一对齐
（12 轮 / 2048 / 512 / 同一判分栈）。

### 3.3 闭环结论（真实结果）

| 指标 | base | lora（step-50） |
|---|---|---|
| pass@4 | **15.0%**（6/40） | 10.0%（4/40） |
| 轨迹级通过率 | 5.0%（8/160） | **5.0%（8/160）** |
| 每题难度画像 | 85% 题 4 次全败 | 90% |

**结论（负结果如实报告）**：50 步训练未带来可测提升；但闭环本身工作正常，
且验证揭示了**下一轮的方向**（85% 题零信号 = 数据难度不匹配；"会做但不稳"
= pass@4 是 pass@1 的 3 倍）。

## 4. 闭环的工程保证（为什么这些数字可信）

| 保证 | 实现 |
|---|---|
| **判分同源** | 训练与评估用同一套 `EpisodeSession` / `evaluate_patch`——绝无双标 |
| **协议同构** | 12 轮 / action 2048 / observation 512 / temp 0.7——逐参数对齐 |
| **防泄漏** | 评估集与训练集 0 重叠（双断言） |
| **证据链** | 每个数字可追到：命令级 execution.json → 判分 test.log → 汇总 CSV |
| **可复现** | 冻结代码包（173 文件 + 校验和）+ 全量归档（本机 + CFS 双份） |

## 5. 闭环数字账

| 环节 | 量级 |
|---|---|
| 沙箱生命周期 | 训练 ~4000 次 + 评估 ~360 次（创建→执行→销毁） |
| 命令级交互 | 数万次（每次 0.1-30 秒） |
| 数据产出 | 训练 1692 轨迹 + 评估 320 轨迹 + 3384 命令证据 |
| 存储占用 | CFS 640GB（模型 122GB 双份 + 检查点 + 轨迹） |
| GPU 时长 | 训练 21 小时 + 评估 ~5 小时（4×L20） |

## 6. 闭环改进路线（下一轮，已识别）

1. **数据侧**：难度画像筛选（保留 pass@4 ∈ 1/4~3/4 的题）——把"零信号题"从训练集剔除；
2. **训练侧**：lr ×10、LoRA 挂 all-linear（含专家层）、预算 8192→16384、n 4→8（见配置审计）；
3. **评估侧**：评估集扩到 100+ 题（当前 40 题分辨率不足）；
4. **闭环自动化**：验证结论 → 数据筛选 → 重训——做成一条可重复的流水线。
