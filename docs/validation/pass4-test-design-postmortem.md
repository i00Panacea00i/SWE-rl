# pass@4 测试设计复盘（2026-09-21）

> 为回答"50 步 LoRA 训练是否提升能力上界"，在 base vs lora 对照上补跑 pass@4
> （4 采样/题）。本文复盘**测试设计本身**：目标、协议、执行中暴露的 4 类缺陷、
> 结果有效性评估、下一轮改进。结果数据与判分证据见
> `artifacts/archive/pass4-eval-20260921/`（本机 + CFS `archive/` 双份）。

---

## 1. 为什么需要这个测试（设计目标）

前序评估（n=1 greedy, temp=0）显示：base pass@1 = 5%（2/40）、lora = 2.5%（1/40），
且 38/40 题的 f2p 全零。**单次采样的信息不足以定性**——存在两种互斥解释：

| 假设 | 含义 | 训练对策 |
|---|---|---|
| H1 "会做但不稳" | 模型有能力，采样运气差 | 巩固稳定性（RL 方向正确，数据难度尚可） |
| H2 "能力断崖" | 模型完全不会 | 更换可学习区间的数据 |

**pass@4 的设计目标**：用 4 次独立采样探测每题的真实成功率，把 H1/H2 区分开，
并为后续训练数据选择提供"难度画像"。

---

## 2. 协议设计

| 维度 | 设计 | 理由 |
|---|---|---|
| 采样 | n=4, **temperature=0.7** | greedy 下 4 次采样完全相同（pass@4≡pass@1）；0.7 与训练 rollout 同温 |
| 评估集 | 40 题 heldout（与训练 0 重叠） | 与 n=1 评估同集，保持跨方法可比 |
| 判分 | `EpisodeSession` + `evaluate_patch`（全新沙箱） | 与训练判分同源，杜绝双标 |
| 分批 | `--n 2 --sample-offset 0/2`，每批 80 沙箱 | **AGS 沙箱实例配额 = 100**；目录名 `__s0..s3` 无冲突，跑完跨批聚合 |
| 准入 | 每批前配额探针（创建即停） | STOPPED 实例在 TTL 到期前仍占配额、平台无删除 API |
| 输出 | pass@k（题级 any）、轨迹级通过率、f2p、**每题成功次数分布** | 前三项判效果；第四项即"难度画像"（意外成为最高价值产出） |

## 3. 执行时间线：四轮才跑通（缺陷链）

```
① 09-20 13:36  首跑 n=4 单批（160 沙箱）
   → ✗ 仅 100 个创建成功：AGS 配额 100 截断，后 15 题完全无数据（顺序截断，非随机）

② 09-20 14:17  链脚本自动跑 4 批 → ✗ 4 批全部 1 分钟内 Failed
   → 根因 A：清单 nodeName 硬编码旧节点 10.0.0.x；该节点被释放 → Pod 无法调度
   → 根因 B：链尾汇总在 sync Pod 执行 → 该 Pod 无 python3（汇总失败）

③ 09-21 04:20  新节点 10.0.0.x 就绪，重启 → ✗ base-p4a/b 再次秒退
   → 根因：driver 已更新（--sample-offset）但 kit 的 protocol.sha256 未重新生成
          → 清单首步 `sha256sum --status -c protocol.sha256` 失败 → set -euo pipefail 立即退出

④ 09-21 04:29  重新生成校验和（281 文件）→ ✓ 全线跑通（每批 ~30 分钟）
   base-p4a 04:59 | base-p4b 05:23 | lora-p4a 05:52 | lora-p4b 06:18 → 自动汇总
```

**值得注意**：②③ 两轮失败都发生在"启动 60 秒内"——这是**快速失败**的正面案例：
校验和/调度错误在设计上就是"启动即暴露"，没有浪费任何生成时间。

## 4. 设计缺陷清单与修复状态

| # | 缺陷 | 症状 | 已修复（本轮） | 治本方案（建议） |
|---|---|---|---|---|
| 1 | 配额未纳入设计 | 160 > 100 截断 | 分批 + `--sample-offset` + 批前探针 | 把"单批沙箱数 ≤ 配额 × 0.8"写进 driver 校验/文档 |
| 2 | nodeName 硬编码 | 节点更替后全批失败 | 手动更新 4 份清单 | 改 `nodeSelector`（GPU 型号标签）由调度器选节点 |
| 3 | 校验和未随代码同步 | 启动秒退 | 重新生成 protocol.sha256 | 上传脚本内固化"上传后即重建校验和"步骤；或清单允许缺失时跳过 |
| 4 | 汇总依赖第三方 Pod | sync Pod 无 python3 | 移至最后批次末尾执行 | 独立"汇总 Pod"清单（自带运行时） |
| 5 | 中断无失败留痕 | 首跑被删后无记录 | driver 新增 `failed_jobs.json` | 失败任务自动补跑模式（driver 支持 `--jobs-file`） |

## 5. 结果有效性评估（复盘的核心）

**得到的数据**（40 题 × 4 采样 × 2 组 = 320 条轨迹，全部有效判分）：

| 指标 | base | lora | 判读 |
|---|---|---|---|
| pass@4（题级 any） | **15.0%** (6/40) | 10.0% (4/40) | 6 vs 4，n=40 **不显著**（二项 p≈0.5） |
| 轨迹级通过率 | **5.0%** (8/160) | **5.0%** (8/160) | **完全相同**——最有力的"无提升"证据 |
| f2p 部分通过 | 6.97% | 7.48% | 微弱差异，不构成改进 |
| 0/4 全失败题 | 34/40（85%） | 36/40（90%） | **85%+ 的题零信号**（GRPO 无梯度来源） |
| 稳定通过（4/4） | 0 题 | 0 题 | 连"会做"的题都不稳定 |

**设计有效性的自评**：

1. **成功回答了设计问题**：pass@4 (15%) = pass@1 greedy (5%) 的 **3 倍** →
   H1（会做但不稳）成立、H2 被推翻——**测试目的达成**。
2. **分辨率局限**：题级 pass@4 的 1 题 = 2.5pp。要检测"训练带来 5pp 提升"需要
   ~160 题/组（或每题更多采样）。**40 题只够定性，不够定量**。
3. **最强的指标不是 pass@4，是轨迹级通过率**（n=160 的伯努利，分辨率 ±1.2pp/0.6%）——
   下轮应把它列为**主指标**，pass@4 为辅助。
4. **难度画像（0/4 vs 1-3/4 vs 4/4）成为最高价值产出**——它直接回答"哪些题能提供
   训练信号"，其价值超过了原定的"组间比较"。
5. **局限声明**：单一评估集（40 题）、单一 checkpoint（step-50）、单一温度（0.7）——
   结论外推到其他数据分布时需谨慎。

## 6. 下一轮测试设计的改进（直接可执行）

1. **评估集扩到 ≥100 题**（现有池 113 题可支撑；需先完成 81 题双向验证）
2. **主指标改为轨迹级通过率**（pass@1 同义，分辨率最高）；pass@4 作能力上界辅助
3. **预注册成功判据**：跑之前写死阈值（如"轨迹级通过率提升 ≥3pp 且 ≥2× 基线噪声"），
   防止事后解读——本轮"6 vs 4"的教训
4. **难度画像模块化**：把"每题 4 采样成功率"固化为数据管线的一步（可复用
   `eval_driver.py`），用于**训练集筛选**（优先 1/4~3/4 的题）
5. **基础设施 checklist 固化**（防再犯）：
   - [ ] AGS 配额余量 ≥ 单批沙箱数（探针）
   - [ ] 节点选择用 nodeSelector（不硬编码 IP）
   - [ ] 上传代码后重建 protocol.sha256
   - [ ] 汇总不依赖第三方 Pod
   - [ ] 失败任务留痕（failed_jobs.json）
6. **保留协议参数**（n=4、temp=0.7、同一判分栈）——跨轮可比是长期价值

## 7. 与验证阶段 ADR 的协议符合性

| ADR | 原设计 | 实际执行 | 符合性 |
|---|---|---|---|
| ADR-001 测试集 | 86 题全量验证后冻结（~70 题）+ 防泄漏断言 | 40 题 heldout（验证流因资源暂停先行开测） | **部分**：题量缩水；防泄漏保持（与训练 0 重叠） |
| ADR-002 协议 | 双协议：temp0 主 + temp0.7×n4 副 | temp0 n=1；temp0.7 n=4（分 2 批采样） | **符合**（分批是配额适配，协议语义不变） |
| ADR-003 架构 | verl val 路径（复用已验证链路） | **独立 vLLM driver**（val 路径共卡 OOM 5 连败） | **偏离（已记录）**：判分栈与训练同源，公平性不受影响；理由见 `troubleshooting/08` |
| ADR-004 判定 | Δ>0 即认可 + Wilson CI + McNemar + 分层报告 | 负结果如实报告 ✓ | **待补**：统计检验（Wilson CI / McNemar）未计算，下轮报告补齐 |

**架构偏离的净影响**：独立 driver 消除了训练栈常驻显存（评估从"44.2/44.39GB 贴线"
变为"每卡 ~30GB 余量"），且两组同栈对比，公平性无损——**偏离被判定为可接受**。
